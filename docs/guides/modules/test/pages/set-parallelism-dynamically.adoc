= Set parallelism dynamically
:page-platform: Cloud
:page-vcs: all
:page-plan: Free, Performance, Scale
:page-audience: developer
:experimental:
:page-description: Set a test job's parallelism when the pipeline runs, based on the number of test atoms it will run, with experimental dynamic parallelism.

Dynamic parallelism sets the `parallelism` of a test job when your pipeline runs, instead of using a fixed value in your configuration. An upstream job counts the test atoms that the test job will run. CircleCI then sets the test job's parallelism from that count, within a minimum and maximum that you choose. When fewer test atoms need to run, the test job uses fewer parallel nodes.

NOTE: Dynamic parallelism is experimental. The `experimental.dynamic-parallelism` configuration will be replaced in a future release. You will be required to update your configuration when the syntax changes.

[#use-with-test-impact-analysis]
== Use with test impact analysis

With test impact analysis, test selection often runs only a small part of your test suite on feature branches. Dynamic parallelism sets the test job's parallelism from the number of selected test atoms, so you do not run more parallel nodes than the selected test atoms need.

=== Prerequisites

Before you set parallelism dynamically, ensure you have:

* Completed the xref:getting-started-with-smarter-testing.adoc[Getting Started With Smarter Testing] guide.
* Set up xref:set-up-test-impact-analysis.adoc[Test Impact Analysis], which has a credit charge above your plan's allowance.
* Test timings for your test suite. Smarter Testing generates timings whenever it runs the full test suite. To generate them, merge to your default branch, or run the test suite once with the `--run-tests=all` flag.

=== How it works

Use the `circleci testsuite list-tests` command in an upstream job to select test atoms, then run the test atoms in a downstream job with parallelism set from the number of selected test atoms.

The `list-tests` command selects test atoms without running them, applying the same selection rules as `circleci testsuite run`. The count reflects what the test job runs. The `--run-tests` and `--analyze-tests` flags accept the same values as `run`. If your test job passes either flag, pass the same flags to `list-tests` so the count matches. See xref:set-up-test-impact-analysis.adoc#overriding-tests-selected-for-run-and-analysis[Overriding Tests Selected for Run and Analysis].

=== Configure dynamic parallelism

Pass a unique key to `list-tests` with the `--key` flag. Then add an `experimental.dynamic-parallelism` stanza to your configuration, including the following:

* The name of the downstream test job.
* The unique key.
* Minimum and maximum parallelism for the job.

.CircleCI configuration that sets parallelism from the selected test atoms
[source,yaml]
----
# .circleci/config.yml
version: 2.1

jobs:
  list-tests:
    executor: my-executor
    steps:
      # Check out the code and install the dependencies the discover command needs.
      - setup
      # List the test atoms that would be selected, without running them.
      - run: circleci testsuite list-tests "ci tests" --key=ci-tests-parallelism-key

  test:
    executor: my-executor
    # Set job parallelism to the maximum parallelism for a full suite to run.
    # Any failures will fall back to this value.
    # This is optional but recommended.
    parallelism: 20
    steps:
      - setup
      - run: circleci testsuite run "ci tests"
      - store_test_results:
          path: test-reports

workflows:
  test-workflow:
    jobs:
      - list-tests
      - test:
          requires:
            - list-tests

experimental:
  dynamic-parallelism:
    # The name of the job to set parallelism for.
    test:
      # Must match the key passed to list-tests.
      key: ci-tests-parallelism-key
      min: 1
      max: 20
----

TIP: The `list-tests` job runs your `discover` command, so it needs a checkout and any dependencies that command relies on.
