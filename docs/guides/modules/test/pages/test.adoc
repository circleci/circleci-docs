CircleCI allows you to automatically test your code before changes are merged. You can integrate testing tools and frameworks such as Jest, Mocha, `pytest`, JUnit, Selenium, XCTest, and more. This page covers the basics that apply to every project, then helps you <<choose-your-test-tooling,choose your test tooling>>.

[#run-tests-in-ci]
== Run tests in CI

When you integrate your tests into your CircleCI pipelines, you deliver software to your users more reliably and efficiently, and get faster feedback. This also means you can fix issues and failed tests faster. Test output data becomes available in CircleCI to help debug failed tests. If you save your test data in CircleCI, you can also split your tests across parallel execution nodes to reduce test time.
ifndef::server[]
Test Insights then helps you find flaky and slow tests.
endif::server[]

To automatically run your test suites in a project pipeline, you will add configuration keys in your `.circleci/config.yml` file. These would typically be defined as a *step* or collection of steps to be executed in a *job*.

A pipeline might consist of a single workflow, with a single job defined that includes a step to execute a suite of tests within an execution environment.

include::ROOT:partial$notes/docker-auth.adoc[]

[,yaml]
----
jobs:
  build-and-test:
    docker:
      - image: cimg/node:24.16.0
    steps:
      - checkout
      - node/install-packages:
          pkg-manager: npm
      - run:
          name: Run tests
          command: npm test
----

`run` is a built-in step that runs commands in a shell. To read more about the `run` step for executing tests and other commands, go to the xref:reference:ROOT:configuration-reference.adoc[Configuration Reference] page.

ifndef::server[]
This example runs your test command directly. On CircleCI Cloud, the recommended way to run tests is to replace that command with `circleci testsuite run`, which adds Smarter Testing capabilities such as test splitting and rerunning only failed tests. See <<choose-your-test-tooling,Choose your test tooling>>.

For example, for a project that uses Vitest, the job runs `circleci testsuite run` in place of the test command:

.`.circleci/config.yml`
[,yaml]
----
jobs:
  build-and-test:
    docker:
      - image: cimg/node:24.16.0
    steps:
      - checkout
      - node/install-packages:
          pkg-manager: npm
      - run:
          name: Run tests
          command: circleci testsuite run "ci tests"
      - store_test_results:
          # Must match outputs.junit in test-suites.yml
          path: test-reports
----

A `.circleci/test-suites.yml` file tells `circleci testsuite` how to discover and run your tests:

.`.circleci/test-suites.yml`
[,yaml]
----
name: ci tests
discover: npx vitest list --filesOnly
run: npx vitest run --reporter=junit --outputFile="<< outputs.junit >>" --silent --bail 0 << test.atoms >>
outputs:
  junit: test-reports/junit.xml
----
endif::server[]
ifdef::server[]
This example runs your test command directly. To split your tests across parallel execution nodes, see <<choose-your-test-tooling,Choose your test tooling>>.

For example, for a project that uses Vitest, the following job splits the test files across four parallel execution nodes using timing data from previous runs:

.`.circleci/config.yml`
[,yaml]
----
jobs:
  build-and-test:
    docker:
      - image: cimg/node:24.16.0
    parallelism: 4
    steps:
      - checkout
      - node/install-packages:
          pkg-manager: npm
      - run:
          name: Run tests
          command: |
            TESTFILES=$(circleci tests glob "src/**/*.test.js" | circleci tests split --split-by=timings)
            npx vitest run --reporter=junit --outputFile=test-results/junit.xml $TESTFILES
      - store_test_results:
          path: test-results
----
endif::server[]

You might also want to require that a test job is run only if a preceding build job is successful.
endif::server[]

[#timing-tab]
=== Timing tab

The *Timing* tab in the *Job Details* UI shows how long each step of a job took. Use it to identify which steps take the most time, so that you can make targeted improvements to reduce overall runtime.

[#test-uploads]
== Test uploads

Use the `store_test_results` step to upload your test results to CircleCI:

[,yaml]
----
steps:
  ... # Steps to build and test your application
  - store_test_results:
      path: test-results
----

This step uploads and stores test results, and also enables direct access to output from failed tests on the *Tests* tab of a job in the web app.

More details on `store_test_results` can be found on the xref:reference:ROOT:configuration-reference.adoc#storetestresults[Configuration Reference] page. For more detailed examples of storing test data with different testing frameworks, refer to the xref:collect-test-data.adoc[Upload Test Results] page.

[#store-test-results-as-artifacts]
== Store test results as artifacts

You can also store test results as artifacts using the `store_artifacts` step. Artifacts are files you can download later. They do not appear on the *Tests* tab.

[,yaml]
----
steps:
  ... # Steps to build and test your application
  - store_artifacts:
      path: test-results
      destination: junit
----

Results can later be accessed or downloaded as files via the *Artifacts* section of a job in the CircleCI web app, or through the API.

More details on `store_artifacts` can be found in the xref:reference:ROOT:configuration-reference.adoc#storeartifacts[Configuration Reference] page. You can also read more in the xref:optimize:artifacts.adoc[Storing Build Artifacts] guide.

[#choose-your-test-tooling]
== Choose your test tooling

ifndef::server[]
On CircleCI Cloud, use Smarter Testing to run your tests. Smarter Testing replaces your test command with `circleci testsuite run`, which discovers and runs your tests. You get the following benefits:

* *Free capabilities with no extra configuration*: static test splitting across parallel nodes, rerunning only failed tests when you rerun a workflow from failed, and test uploads.
* *Faster test runs when you need them*: test impact analysis runs only the tests impacted by your code changes. Dynamic test splitting keeps parallel nodes evenly loaded. Auto rerun failed tests retries flaky tests automatically. These capabilities have a credit charge above your plan's allowance.
* *The same command locally and in CI*: run and validate your test setup on your own machine before you push.

To learn more, read the xref:smarter-testing-overview.adoc[Smarter Testing Overview], then follow xref:getting-started-with-smarter-testing.adoc[Getting Started With Smarter Testing].

TIP: You can use the xref:toolkit:circleci-agent-skills.adoc[CircleCI Agent Skills] to get set up for Smarter Testing. Install the link:https://github.com/CircleCI-Public/skills[CircleCI Public Skills] plugin to your AI coding agent and ask your agent to get set up for Smarter Testing.

If your project already uses the `circleci tests glob`, `circleci tests split`, or `circleci tests run` commands, they continue to work. See xref:optimize:parallelism-faster-jobs.adoc[Test Splitting and Parallelism] and xref:rerun-failed-tests.adoc[Rerun Failed Tests With the Tests Run Command].
endif::server[]
ifdef::server[]
To split your tests across parallel execution nodes, use the `circleci tests glob` and `circleci tests split` commands. These commands are part of the environment CLI, which is available in every job, so there is nothing to install. See xref:optimize:parallelism-faster-jobs.adoc[Test Splitting and Parallelism] and xref:optimize:use-the-circleci-cli-to-split-tests.adoc[Use the Environment CLI to Split Tests].

The `circleci tests run` command and Smarter Testing are available on CircleCI Cloud only.
endif::server[]
