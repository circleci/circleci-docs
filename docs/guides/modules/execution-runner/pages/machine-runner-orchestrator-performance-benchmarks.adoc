= Machine runner orchestrator performance benchmarks
:page-platform: Cloud, Server v4+
:page-description: Performance benchmarks for machine runner orchestrator under increasing load, covering VM provisioning queue times and throughput across resource classes.
:experimental:

Machine runner orchestrator (MRO) auto-scales KubeVirt virtual machines to serve CircleCI self-hosted runner jobs.
Its scaling behavior is directly affected by how you configure `maxReplicas`, node capacity, and resource class sizing.

By publishing these benchmarks, CircleCI can show the measurable performance characteristics of MRO under realistic load and help operators choose configurations that meet their throughput and latency goals.
For an overview of machine runner orchestrator concepts and setup, see xref:execution-runner:runner-provisioner.adoc[Machine Runner Orchestrator Overview].

NOTE: These benchmarks reflect a specific test cluster configuration described below.
Actual results vary depending on your node types, autoscaler settings, and resource class definitions.

[#test-environment]
== Test environment

All three experiments ran against the same Kubernetes cluster.
Nodes used the c8i.12xlarge instance type (48 vCPU / 96 GiB RAM), with a cluster autoscaler ASG of 2–6 nodes and KubeVirt enabled on all nodes.

The experiments used two resource classes:

[.table-scroll]
--
[cols="4", options="header"]
|===
| Resource class | VM size | `minReplicas` | `maxReplicas`

| `circleci-runner/rp-stress-high`
| 8 vCPU / 32 GiB
| 2
| 9

| `circleci-runner/rp-stress-low`
| 2 vCPU / 8 GiB
| 2
| 34
|===
--

Both resource classes shared the same node group.
The high-class `maxReplicas` value of 9 reflects a memory constraint.
The shared node group has 344 GiB total allocatable memory, and 9 × 32 GiB high-class VMs consume most of it.

[#test-method]
== Test method

Each experiment triggered 130 jobs in four escalating steps:

[.table-scroll]
--
[cols="4", options="header"]
|===
| Step | Trigger rate | Jobs in step | Hold duration

| 0
| 1 job/min
| 10
| 600 s

| 1
| 2 jobs/min
| 20
| 600 s

| 2
| 4 jobs/min
| 40
| 600 s

| 3
| 6 jobs/min
| 60
| 600 s
|===
--

Every job ran `sleep 300` (5 minutes of actual work), so:

----
total duration = queue time + 300 s
----

The test ran three experiments:

* *High-only*: all 130 jobs used the high resource class.
* *Low-only*: all 130 jobs used the low resource class.
* *Mixed*: the test randomly assigned each job to either the high or low resource class.

The tables below report queue time and total job duration at the 50th and 90th percentiles (p50/p90) for each step.
*Saturated* indicates that queue times grew consistently across the step, meaning the scaler did not provision VMs fast enough to match the arrival rate.

The system handled steps 0 and 1 (up to 2 jobs/min) without saturation.
At step 2 (4 jobs/min), queue p90 jumped from 82 s to 518 s.

All 130 jobs completed with zero errors, but wait times at steps 2 and 3 make these rates unsuitable for latency-sensitive workloads.

The bottleneck is `maxReplicas`=9.
When arrival rate exceeds what 9 running VMs can turn over, the queue grows until enough VMs finish and free capacity.

[#configuration-recommendations]
== Configuration recommendations

[#set-the-replica-limit-for-the-expected-peak]
=== Set the replica limit for the expected peak

The `maxReplicas` limit is the most direct lever for queue time.
In the high-only run, the 9-replica cap meant that jobs arriving at 4–6/min stacked up behind the fixed pool of VMs.
A higher `maxReplicas` allows more VMs to run concurrently, reducing queue buildup.

When sizing `maxReplicas` for a resource class, calculate the number of VMs that fit on your node group at peak capacity:

----
maxReplicas ≤ floor(total allocatable memory / VM memory)
----

Subtract a buffer for the OS and Kubernetes system pods.

[#account-for-shared-node-groups]
=== Account for shared node groups

When multiple resource classes share a node group, each class competes for the same physical memory.
The sum of `maxReplicas × VM memory` across all resource classes must not exceed the node group's total allocatable memory.
If one class has a generous `maxReplicas`, it may starve the other.

[#use-mixed-resource-classes-to-reduce-peak-pressure]
=== Use mixed resource classes to reduce peak pressure

Routing traffic across resource classes of different sizes reduces queue times for the larger class.
If your workload includes jobs with different resource requirements, define appropriately sized resource classes for each job type rather than routing everything through a single large class.

[#add-headroom-for-burst-traffic]
=== Add headroom for burst traffic

MRO supports a `headroom` configuration that provisions extra VMs beyond the current task count.
Setting headroom ensures idle VMs are available when a burst of jobs arrives, reducing the delay from VM cold-start.
Headroom is most effective for large resource classes where VM provisioning time adds noticeably to queue latency.
