= Migrate from API v1 and v1.1 to v2 or v3
:page-platform: Cloud, Server
:page-server-min-version: "4.7"
:page-vcs: all
:page-plan: Free, Performance, Scale
:page-audience: developer
:page-description: Step-by-step guide to migrate from deprecated CircleCI API v1 and v1.1 trigger and rerun endpoints to API v2 or v3 before the 1 February 2027 removal date.
:experimental:

Ten v1 and v1.1 API endpoints used to trigger and rerun builds are scheduled for removal on 1 February 2027. See <<deprecated-endpoints>>. After that date, requests to these endpoints return HTTP 410 Gone. This guide walks you through finding those calls in your code, updating your project addressing, and switching to the equivalent v2 or v3 endpoints.

WARNING: Deprecated endpoints now return `Deprecation` and `Sunset` response headers. On 1 February 2027 they return HTTP 410 Gone. Update your integrations before that date.

ifndef::server[]
Cloud customers: CircleCI recommends starting with API v3. API v2 remains supported if v3 does not cover your needs.
endif::server[]
ifdef::server[]
NOTE: API v3 is not available on CircleCI Server. Use the API v2 endpoints described in this guide.
endif::server[]

[#deprecated-endpoints]
== Deprecated endpoints

CircleCI removes the following ten endpoints on 1 February 2027. This change applies to both CircleCI Cloud and CircleCI Server.

v1 endpoints:

* `POST /api/v1/project/:username/:repo/`
* `POST /api/v1/project/:username/:repo/:build_num/retry`
* `POST /api/v1/project/:username/:repo/:build_num/ssh`
* `POST /api/v1/project/:username/:repo/build`
* `POST /api/v1/project/:username/:repo/tree/:branch`

v1.1 endpoints:

* `POST /api/v1.1/project/:vcs-type/:username/:repo/`
* `POST /api/v1.1/project/:vcs-type/:username/:repo/:build_num/retry`
* `POST /api/v1.1/project/:vcs-type/:username/:repo/:build_num/ssh`
* `POST /api/v1.1/project/:vcs-type/:username/:repo/build`
* `POST /api/v1.1/project/:vcs-type/:username/:repo/tree/:branch`

[#prerequisites]
== Prerequisites

* A CircleCI personal API token. See the xref:managing-api-tokens.adoc[Managing API Tokens] guide.
ifndef::server[]
* For API v3: your organization ID and project ID. See xref:how-to-find-ids.adoc[How to Find IDs].
endif::server[]
* For API v2: your project slug in the form `:provider/:organization/:project`, for example `gh/my-org/my-repo`.

[#find-your-v1-api-calls]
== 1. Find your v1 API calls

Search your CI scripts, automation tooling, and third-party integrations for calls to the deprecated endpoints.

Search for the following patterns:

[source,console]
----
$ grep -r "api/v1" .
$ grep -r "api/v1.1" .
----

Look in:

* Shell scripts and Makefiles.
* CI configuration files such as `.circleci/config.yml` and `.github/workflows/`.
* Internal tooling, deployment scripts, and scheduled jobs.
* Third-party integrations and webhook consumers that call back into CircleCI.

For each match, check whether the HTTP method is `POST` and whether the path matches one of the deprecated patterns listed above.

[#update-project-addressing]
== 3. Update project addressing

v1 and v1.1 use different project addressing from v2 and v3.

v1.1 uses `:vcs-type/:username/:project`, for example `github/my-org/my-repo`.

v2 uses `:provider/:organization/:project`. Both the long and short forms of the VCS provider name are accepted:

[.table-scroll]
--
[cols="1,1,1", options="header"]
|===
| Provider | v1.1 `:vcs-type` value | v2 `:provider` value

| GitHub
| `github`
| `github` or `gh`

| Bitbucket
| `bitbucket`
| `bitbucket` or `bb`

| GitLab
| Not supported in v1.1
| `circleci`

|===
--

ifndef::server[]
v3 uses UUIDs for all resources. See xref:how-to-find-ids.adoc[How to Find IDs] to retrieve your organization ID and project ID, or use the API v3 `GET /api/v3/projects` endpoint.
endif::server[]

[#api-examples]
== API examples

The following examples show how to call the replacement endpoints for triggering pipeline runs and rerunning workflows.

[#trigger-a-pipeline-run]
=== Trigger a pipeline run

ifndef::server[]
==== Using API v3

[source,console]
----
$ curl --request POST https://circleci.com/api/v3/runs \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{
    "project_id": "<your-project-uuid>",
    "branch": "main"
  }'
----

See xref:how-to-find-ids.adoc[How to Find IDs] to get your project UUID, or use `GET /api/v3/projects`.

To trigger on a specific branch or tag, include `branch` or `tag` in the request body. To pass pipeline parameters, include a `parameters` object.

endif::server[]

==== Using API v2

[source,console]
----
$ curl --request POST \
  "https://circleci.com/api/v2/project/<provider>/<organization>/<project>/pipeline/run" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{
    "branch": "main"
  }'
----

Replace `<provider>`, `<organization>`, and `<project>` with your project values, for example `gh/my-org/my-repo`. To trigger on a specific branch, include `"branch"`. To pass pipeline parameters, include a `"parameters"` object:

[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v2/project/gh/my-org/my-repo/pipeline/run" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{
    "branch": "main",
    "parameters": {
      "my-param": "my-value"
    }
  }'
----

[#rerun-a-workflow]
=== Rerun a workflow

Rerunning is now workflow-based. You choose which workflow to rerun, and optionally which jobs within it.

Before calling the rerun endpoint, retrieve the workflow ID from the pipeline run response or by calling:

[source,console]
----
$ curl "https://circleci.com/api/v2/pipeline/<pipeline-id>/workflow" \
  --header "Circle-Token: $CIRCLE_TOKEN"
----

ifndef::server[]
==== Using API v3

[source,console]
----
$ curl --request POST \
  "https://circleci.com/api/v3/workflows/<workflow-id>/rerun" \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{}'
----

To rerun only failed jobs:

[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v3/workflows/<workflow-id>/rerun" \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"from_failed": true}'
----

To rerun with SSH enabled:

[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v3/workflows/<workflow-id>/rerun" \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"is_ssh_enabled": true}'
----

endif::server[]

==== Using API v2

[source,console]
----
$ curl --request POST \
  "https://circleci.com/api/v2/workflow/<workflow-id>/rerun" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{}'
----

To rerun only failed jobs:

[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v2/workflow/<workflow-id>/rerun" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"from_failed": true}'
----

To rerun with SSH enabled:

[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v2/workflow/<workflow-id>/rerun" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"enable_ssh": true}'
----

[#response-differences]
== Response differences

The v2 and v3 responses differ from the v1 build-centric format.

v1 and v1.1 triggered a job and returned a build summary with fields like `build_num`, `build_url`, and `status`.

v2 triggers a pipeline run and returns a pipeline object:

[source,json]
----
{
  "id": "5034460f-c7c4-4c43-9457-de07e2029e7b",
  "state": "created",
  "number": 1,
  "created_at": "2020-01-01T15:32:36.605Z"
}
----

Use the returned pipeline `id` to fetch workflow and job details:

[source,console]
----
$ curl "https://circleci.com/api/v2/pipeline/<pipeline-id>/workflow" \
  --header "Circle-Token: $CIRCLE_TOKEN"
----

ifndef::server[]
v3 triggers a run and returns a run object with a `run_id`:

[source,json]
----
{
  "run_id": "c6e2e2cd-d0ee-4253-be29-d076f9555602",
  "created_at": "2020-01-01T15:32:36.605Z"
}
----

Use `GET /api/v3/runs/<run-id>` to retrieve run status and workflow details.
endif::server[]

Key differences to update in your code:

* Replace `build_num` references with pipeline `id` or run `run_id`.
* Replace `build_url` references with links constructed from the pipeline or workflow ID.
* Replace `status` polling on the trigger response with calls to the pipeline or workflow status endpoints.
