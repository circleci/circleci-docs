= Migrate from API v1 and v1.1 to API v2 or v3
:page-platform: Cloud, Server
:page-server-min-version: "4.7"
:page-vcs: all
:page-plan: Free, Performance, Scale
:page-audience: developer
:page-description: Migrate from deprecated CircleCI API v1 and API v1.1 trigger and rerun endpoints to API v2 or API v3 before the 1 February 2027 removal date.
:experimental:

CircleCI removes ten API v1 and API v1.1 endpoints used to trigger and rerun builds on 1 February 2027. See <<deprecated-endpoints>>. After that date, requests to these endpoints return HTTP 410 Gone. This guide walks you through finding those calls in your code and replacing each one with an API v2 or API v3 call.

WARNING: Until the removal date, the deprecated endpoints return `Deprecation` and `Sunset` response headers. Update your integrations before 1 February 2027.

ifndef::server[]
NOTE: API v3 is currently available on CircleCI Cloud only. CircleCI Server customers use API v2. The API v2 steps in this guide apply to both Cloud and Server.

CircleCI recommends starting with API v3 on Cloud. API v2 remains supported if API v3 does not cover your needs.
endif::server[]
ifdef::server[]
NOTE: API v3 is not available on CircleCI Server. Use the API v2 endpoints described in this guide.
endif::server[]

[#deprecated-endpoints]
== Deprecated endpoints

CircleCI removes the following ten endpoints on 1 February 2027. This change applies to both CircleCI Cloud and CircleCI Server.

API v1 endpoints:

* `POST /api/v1/project/<username>/<repo>/`
* `POST /api/v1/project/<username>/<repo>/<build-num>/retry`
* `POST /api/v1/project/<username>/<repo>/<build-num>/ssh`
* `POST /api/v1/project/<username>/<repo>/build`
* `POST /api/v1/project/<username>/<repo>/tree/<branch>`

API v1.1 endpoints:

* `POST /api/v1.1/project/<vcs-type>/<username>/<repo>/`
* `POST /api/v1.1/project/<vcs-type>/<username>/<repo>/<build-num>/retry`
* `POST /api/v1.1/project/<vcs-type>/<username>/<repo>/<build-num>/ssh`
* `POST /api/v1.1/project/<vcs-type>/<username>/<repo>/build`
* `POST /api/v1.1/project/<vcs-type>/<username>/<repo>/tree/<branch>`

All other API v1 and API v1.1 endpoints, including every `GET` endpoint, are not affected. API v2 and API v3 endpoints are not affected.

[#prerequisites]
== Prerequisites

* A CircleCI personal API token. API v2 does not support project API tokens. See the xref:managing-api-tokens.adoc[Managing API Tokens] guide.
ifndef::server[]
* For API v3: your project ID. You use it to list the project's pipeline definitions. See xref:how-to-find-ids.adoc[How to Find IDs] for steps to find it.
endif::server[]
* For API v2: your project slug in the form `<provider>/<organization>/<project>`, for example `gh/my-org/my-repo`. See <<project-addressing>>.

[#find-your-v1-api-calls]
== 1. Find your API v1 and v1.1 calls

Search your CI scripts, automation tooling, and third-party integrations for calls to the deprecated endpoints.

Search for the following pattern:

[source,console]
----
$ grep -rE "api/v1(\.1)?/project" .
----

Look in:

* Shell scripts and `Makefile` build files.
* CI configuration files such as `.circleci/config.yml` and `.github/workflows/`.
* Internal tooling, deployment scripts, and scheduled jobs.
* Third-party integrations and webhook consumers that call back into CircleCI.

For each match, check whether the HTTP method is `POST` and whether the path matches one of the deprecated endpoints listed in <<deprecated-endpoints>>.

[#project-addressing]
=== Find your project address

API v1.1 identifies a project by `<vcs-type>/<username>/<repo>`. API v2 identifies it by a project slug, `<provider>/<organization>/<project>`, which you put in the URL of each request:

* `<vcs-type>` becomes `<provider>`.
* `<username>` becomes `<organization>`.
* `<repo>` becomes `<project>`.

API v1 has no VCS type in the path, so work out the provider for each project before you move to API v2. To find the provider and the full slug:

. Open the project in the CircleCI web app.
. Go to *Project Settings > Overview*. This page shows the project slug.

ifndef::server[]
The web app URL uses the long provider form. For example, `https://app.circleci.com/pipelines/github/my-org/my-repo` uses `github`. API v2 accepts both the long and short form, so `github/my-org/my-repo` and `gh/my-org/my-repo` are the same project.
endif::server[]
ifdef::server[]
API v2 accepts both the long and short form of the provider name, so `github/my-org/my-repo` and `gh/my-org/my-repo` are the same project.
endif::server[]

[.table-scroll]
--
[cols="1,1,1", options="header"]
|===
| Provider | API v1.1 `<vcs-type>` value | API v2 `<provider>` value

| GitHub
| `github`
| `github` or `gh`

| Bitbucket
| `bitbucket`
| `bitbucket` or `bb`

|===
--

Projects in some organizations have an opaque project slug, for example `circleci/<organization-id>/<project-id>`. Use the slug that *Project Settings > Overview* shows. API v1 and API v1.1 cannot address these projects.

ifndef::server[]
API v3 identifies resources by UUID instead of by name, so you need your project ID instead of a project slug. See xref:how-to-find-ids.adoc[How to Find IDs] for steps to find them, or use the API v3 `GET /api/v3/projects` endpoint.
endif::server[]

[#authentication]
=== Update authentication

API v2 and API v3 accept the personal API token in an HTTP header:

[.table-scroll]
--
[cols="1,2", options="header"]
|===
| API version | How to send the token

| API v1 and v1.1
| The `Circle-Token` header, the `Authorization: Bearer` header, HTTP basic authentication, or the `circle-token` query parameter.

| API v2
| The `Circle-Token` header or the `Authorization: Bearer` header. HTTP basic authentication is also accepted. CircleCI has deprecated the `circle-token` query parameter.

ifndef::server[]
| API v3
| The `Authorization: Bearer` header.
endif::server[]

|===
--

If your API v1 or API v1.1 calls pass the token as a query parameter, move it to a header. If they use a project API token, create a personal API token instead.

[#trigger-a-pipeline-run]
=== Trigger a pipeline run

Three API v1.1 endpoints become one API v2 endpoint and one API v3 endpoint. The branch moves from the URL path (`/tree/<branch>`) into the request body.

ifndef::server[]
==== Using API v3

. Find your pipeline definition ID. A pipeline definition tells CircleCI which repository and config file to use for a pipeline. A project can have more than one, so the trigger request names the one to run. In the web app, go to *Project Settings > Pipelines*. You can also list the definitions for a project with the API:
+
[source,shell]
----
curl -g "https://circleci.com/api/v3/pipelines?filter[project_id]=<project-id>" \
  --header "Authorization: Bearer $CIRCLE_TOKEN"
----
. Trigger the run. Send the pipeline definition ID in `references.pipeline.id`:
+
[source,shell]
----
curl --request POST https://circleci.com/api/v3/runs \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{
    "data": {
      "attributes": {
        "config": { "branch": "main" },
        "checkout": { "branch": "main" }
      },
      "references": {
        "pipeline": { "id": "<pipeline-definition-id>" }
      }
    }
  }'
----
. The response contains the run ID in `data.id`. You need it to find the run's workflows and to check its status:
+
[source,json]
----
{
  "data": {
    "id": "<run-id>",
    "attributes": {
      "created_at": "2020-01-01T15:32:36.605Z"
    },
    "references": {
      "pipeline": { "id": "<pipeline-definition-id>" },
      "project": { "id": "<project-id>" },
      "user": { "id": "<user-id>" }
    }
  }
}
----

endif::server[]

ifndef::server[]
==== Using API v2

. Find your pipeline definition ID. A pipeline definition tells CircleCI which repository and config file to use for a pipeline. A project can have more than one, so the trigger request names the one to run. In the web app, go to *Project Settings > Pipelines*. You can also list the definitions for a project with the API:
+
[source,shell]
----
curl "https://circleci.com/api/v2/project/<provider>/<organization>/<project>" \
  --header "Circle-Token: $CIRCLE_TOKEN"
----
+
Take the project `id` from the response. The pipeline definitions endpoint needs it in place of the slug:
+
[source,shell]
----
curl "https://circleci.com/api/v2/projects/<project-id>/pipeline-definitions" \
  --header "Circle-Token: $CIRCLE_TOKEN"
----
. Trigger the pipeline run. Send the pipeline definition ID in `definition_id`:
+
[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v2/project/<provider>/<organization>/<project>/pipeline/run" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{
    "definition_id": "<pipeline-definition-id>",
    "config": { "branch": "main" },
    "checkout": { "branch": "main" }
  }'
----
. The response contains the pipeline `id` and `number`. You need the `id` to find the pipeline's workflows, and the `number` to build a link to the pipeline in the web app:
+
[source,json]
----
{
  "id": "<pipeline-id>",
  "number": 1,
  "state": "pending",
  "created_at": "2020-01-01T15:32:36.605Z"
}
----

endif::server[]
ifdef::server[]
==== Using API v2

. Trigger the pipeline run. Send the branch in `branch`:
+
[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v2/project/<provider>/<organization>/<project>/pipeline" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"branch": "main"}'
----
. The response contains the pipeline `id` and `number`. You need the `id` to find the pipeline's workflows, and the `number` to build a link to the pipeline in the web app:
+
[source,json]
----
{
  "id": "<pipeline-id>",
  "number": 1,
  "state": "pending",
  "created_at": "2020-01-01T15:32:36.605Z"
}
----
endif::server[]

[#trigger-parameters]
==== Move your trigger parameters

ifndef::server[]
In the request body, `config` sets the branch or tag that CircleCI reads your config file from. `checkout` sets the branch or tag that the `checkout` step checks out. Use the same reference type, `branch` or `tag`, in both. Mixing them returns an error.

The API v1.1 request body fields map as follows:

* `branch`: Becomes `config.branch` and `checkout.branch`.
* `tag`: Becomes `config.tag` and `checkout.tag`.
* `revision`: No replacement. API v2 and API v3 take a branch or a tag, not a commit.
* `build_parameters`: Environment variables set through `build_parameters` have no direct replacement. Declare a pipeline parameter in your config for each value, then pass the values in `parameters`.

A pipeline parameter that your config does not declare is not rejected when you trigger. The request returns a success response, and the pipeline then fails with the error `Unexpected argument(s): <parameter-name>`.

Pass pipeline parameters in a `parameters` object:

[source,json]
----
{
  "definition_id": "<pipeline-definition-id>",
  "config": { "branch": "main" },
  "checkout": { "branch": "main" },
  "parameters": {
    "<parameter-name>": "<parameter-value>"
  }
}
----
endif::server[]
ifdef::server[]
The API v1.1 request body fields map as follows:

* `branch`: Stays `branch`. The branch moves from the URL path (`/tree/<branch>`) into the request body.
* `tag`: Stays `tag`. Use either `branch` or `tag`, not both.
* `revision`: No replacement. API v2 takes a branch or a tag, not a commit.
* `build_parameters`: Environment variables set through `build_parameters` have no direct replacement. Declare a pipeline parameter in your config for each value, then pass the values in `parameters`.

A pipeline parameter that your config does not declare is not rejected when you trigger. The request returns a success response, and the pipeline then fails with the error `Unexpected argument(s): <parameter-name>`.

Pass pipeline parameters in a `parameters` object:

[source,json]
----
{
  "branch": "main",
  "parameters": {
    "<parameter-name>": "<parameter-value>"
  }
}
----
endif::server[]

[#rerun-a-workflow]
=== Rerun a workflow

Rerunning in API v2 and API v3 is workflow-based. You choose which workflow to rerun, and optionally which jobs within it. Every rerun needs a workflow ID, so get that first.

[#get-the-workflow-id]
==== Get the workflow ID

If you saved the response when you triggered the pipeline run, use that:

ifndef::server[]
* API v3: List the workflows for the run, using the run ID from the trigger response:
+
[source,shell]
----
curl -g "https://circleci.com/api/v3/workflows?filter[run_id]=<run-id>" \
  --header "Authorization: Bearer $CIRCLE_TOKEN"
----
* API v2: List the workflows for the pipeline, using the pipeline ID from the trigger response:
+
[source,shell]
----
curl "https://circleci.com/api/v2/pipeline/<pipeline-id>/workflow" \
  --header "Circle-Token: $CIRCLE_TOKEN"
----
endif::server[]
ifdef::server[]
List the workflows for the pipeline, using the pipeline ID from the trigger response:

[source,shell]
----
curl "https://circleci.com/api/v2/pipeline/<pipeline-id>/workflow" \
  --header "Circle-Token: $CIRCLE_TOKEN"
----
endif::server[]

If you only have a build number, which is all the API v1 and API v1.1 retry endpoints needed, look up the job. The response includes the workflow ID in `latest_workflow.id`:

// TODO(DOC-327): Confirm with the API team that GET /project/{project-slug}/job/{job-number} is meant to stay public.
// TODO(DOC-327): It works, and api-developers-guide.adoc documents it, but it is missing from the API v2 OpenAPI spec. Link to the API reference once it is restored.
[source,shell]
----
curl "https://circleci.com/api/v2/project/<provider>/<organization>/<project>/job/<job-number>" \
  --header "Circle-Token: $CIRCLE_TOKEN"
----

See the xref:api-developers-guide.adoc#get-job-details[Get Job Details] section of the API v2 Developers Guide for the full response.

ifndef::server[]
==== Using API v3

Rerun all jobs in the workflow:

[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v3/workflows/<workflow-id>/rerun" \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{}'
----

To rerun only failed jobs, set `is_from_failed` to `true`:

[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v3/workflows/<workflow-id>/rerun" \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"is_from_failed": true}'
----

The response contains the ID of the new workflow in `data.id`.

To rerun with SSH enabled:

. Get the job IDs in the workflow. The SSH rerun request must name the jobs to rerun:
+
[source,shell]
----
curl -g "https://circleci.com/api/v3/jobs?filter[workflow_id]=<workflow-id>" \
  --header "Authorization: Bearer $CIRCLE_TOKEN"
----
. Rerun the workflow with `is_ssh_enabled` set to `true` and the jobs to rerun in `jobs`. You cannot combine `is_ssh_enabled` with `is_from_failed`:
+
[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v3/workflows/<workflow-id>/rerun" \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"is_ssh_enabled": true, "jobs": ["<job-id>"]}'
----

endif::server[]

==== Using API v2

Rerun all jobs in the workflow:

[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v2/workflow/<workflow-id>/rerun" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{}'
----

To rerun only failed jobs, set `from_failed` to `true`:

[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v2/workflow/<workflow-id>/rerun" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"from_failed": true}'
----

The response contains the ID of the new workflow in `workflow_id`.

To rerun with SSH enabled:

. Get the job IDs in the workflow. The SSH rerun request must name the jobs to rerun:
+
[source,shell]
----
curl "https://circleci.com/api/v2/workflow/<workflow-id>/job" \
  --header "Circle-Token: $CIRCLE_TOKEN"
----
. Rerun the workflow with `enable_ssh` set to `true` and the jobs to rerun in `jobs`. You cannot combine `enable_ssh` with `from_failed`:
+
[source,shell]
----
curl --request POST \
  "https://circleci.com/api/v2/workflow/<workflow-id>/rerun" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"enable_ssh": true, "jobs": ["<job-id>"]}'
----

[#update-how-you-track-results]
== 3. Update how you track results

API v1 and API v1.1 triggered a job and returned a build summary with fields such as `build_num`, `build_url`, and `status`. API v2 and API v3 return a pipeline or run object instead. The following sections show how to replace each field.

[#replace-build-num]
=== Replace build numbers

API v1.1 callers used the build number to find a job again. Save the ID from the trigger response instead, and use it to look up the workflows and their status. The examples use https://jqlang.github.io/jq/[jq] to read the response.

ifndef::server[]
For API v3, the run ID is `data.id`:

[source,shell]
----
RUN_ID=$(curl --silent --request POST https://circleci.com/api/v3/runs \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"data": {"attributes": {"config": {"branch": "main"}, "checkout": {"branch": "main"}}, "references": {"pipeline": {"id": "<pipeline-definition-id>"}}}}' \
  | jq --raw-output '.data.id')
----

For API v2, the pipeline ID is `id`:
endif::server[]
ifdef::server[]
The pipeline ID is `id`:
endif::server[]

ifndef::server[]
[source,shell]
----
PIPELINE_ID=$(curl --silent --request POST \
  "https://circleci.com/api/v2/project/<provider>/<organization>/<project>/pipeline/run" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"definition_id": "<pipeline-definition-id>", "config": {"branch": "main"}, "checkout": {"branch": "main"}}' \
  | jq --raw-output '.id')
----
endif::server[]
ifdef::server[]
[source,shell]
----
PIPELINE_ID=$(curl --silent --request POST \
  "https://circleci.com/api/v2/project/<provider>/<organization>/<project>/pipeline" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"branch": "main"}' \
  | jq --raw-output '.id')
----
endif::server[]

[#replace-build-url]
=== Replace build URLs

API v1 and API v1.1 returned a `build_url` in the trigger response. API v2 and API v3 do not return a URL.

ifndef::server[]
Construct the link to the workflow in the CircleCI web app instead. Use the long provider form, such as `github`, in this URL:

[source,text]
----
https://app.circleci.com/pipelines/<provider>/<organization>/<project>/<pipeline-number>/workflows/<workflow-id>
----

For example:

[source,text]
----
https://app.circleci.com/pipelines/github/my-org/my-repo/130/workflows/fda08377-fe7e-46b1-8992-3a7aaecac9c3
----

Take `<pipeline-number>` from the `number` field of the API v2 trigger response. To get `<workflow-id>`, list the workflows in the pipeline:
endif::server[]
ifdef::server[]
To find the workflow in the CircleCI web app, use the `number` field of the trigger response and the workflow ID. To get the workflow ID, list the workflows in the pipeline:
endif::server[]

[source,shell]
----
curl --silent "https://circleci.com/api/v2/pipeline/$PIPELINE_ID/workflow" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  | jq --raw-output '.items[] | "\(.name): \(.id)"'
----

ifndef::server[]
For API v3, get the pipeline number from `GET /api/v3/runs/<run-id>`, where it is in `data.attributes.number`. Get the workflow IDs from `GET /api/v3/workflows?filter[run_id]=<run-id>`.
endif::server[]

[#replace-status-polling]
=== Replace status polling

Poll the workflow instead of the trigger response. In API v2, `GET /api/v2/workflow/<workflow-id>` returns a `status` field:

[source,shell]
----
curl --silent "https://circleci.com/api/v2/workflow/<workflow-id>" \
  --header "Circle-Token: $CIRCLE_TOKEN" \
  | jq --raw-output '.status'
----

Keep polling while the status is one of the following:

* `running`
* `failing`
* `on_hold`: The workflow is waiting for approval. It does not finish until someone approves or cancels it.

The workflow has finished when the status is one of the following:

* `success`
* `failed`
* `error`
* `canceled`
* `not_run`
* `unauthorized`

ifndef::server[]
In API v3, poll the run. `GET /api/v3/runs/<run-id>` returns the state of the run in two fields:

[source,shell]
----
curl --silent "https://circleci.com/api/v3/runs/<run-id>" \
  --header "Authorization: Bearer $CIRCLE_TOKEN" \
  | jq '.data.attributes | {phase, current_outcome}'
----

* `phase` is `queued`, `started`, or `ended`. Keep polling until it is `ended`.
* `current_outcome` is the result so far. It can change after the run ends if you rerun a workflow. The possible values are:
** `succeeded`
** `failed`
** `canceled`
** `errored`
** `not_run`
** `unauthorized`
endif::server[]
