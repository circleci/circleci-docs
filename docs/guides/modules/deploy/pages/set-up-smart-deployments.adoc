= Set up Smart Deployments
:page-platform: Cloud
:page-description: Use the Smart Deployments guided setup to configure deploy markers, deploy and rollback pipelines, deploy validation, and automatic rollback.
:experimental:
:tabs-sync-option:

Smart Deployments is a guided setup in the CircleCI web app. It generates the configuration you need to track your deployments, deploy and roll back from the web app, and validate each release against your monitoring tool.

Smart Deployments is the recommended way to get set up. You answer a few questions in the web app, and CircleCI opens a pull request with the configuration. This replaces working through the deploy marker, rollback pipeline, and deploy pipeline guides separately.

== Introduction

Smart Deployments implements _continuous validation_. After a deploy completes, CircleCI opens an evaluation window and listens for alerts from your monitoring tool. If a signal fails, CircleCI marks the release as failed and can roll back to the last healthy version automatically.

The guided setup offers two protection levels:

* *Continuous validation*: Deploy markers, deploy validation, rollback and deploy pipelines, and automatic rollback. This is the suggested option.
* *Deploy tracking*: Deploy markers only. CircleCI records what shipped and when, with no validation or rollback.

You can start with deploy tracking and move to continuous validation later. Your protection level is not fixed at setup time.

=== What continuous validation provides

When you choose continuous validation, CircleCI configures the following capabilities:

[.table-scroll]
--
[cols="1,2", options="header"]
|===
|Capability
|Description

|Deploy markers
|Records when your deploys start and finish. This is the required baseline for every other capability.

|Deploy validation
|Evaluates webhook signals from your monitoring tool during an evaluation window after each deploy.

|Rollback and deploy pipelines
|Rollback and deploy workflows you can trigger from the web app. Required for automatic rollbacks.

|Automatic rollback
|Reverts to the last healthy version when validation fails, using your rollback pipeline. Optional, and enabled by default.
|===
--

== Prerequisites

Before you start, confirm the following:

* A CircleCI account connected to your code. You can link:https://circleci.com/signup/[sign up for free].
* A CircleCI project with a workflow configured to deploy your code.
* Your code must be stored in a *GitHub* repository. CircleCI installs the GitHub App in your organization during setup if it is not installed already. For more information, see the xref:permissions-authentication:users-organizations-and-integrations-guide.adoc[Users, Organizations, and Integrations Guide].
+
NOTE: Only organization administrators can install the GitHub App. If you use a version control system other than GitHub, see the xref:set-up-deploy-validation-manually.adoc[Set up Deploy Validation Manually] guide instead.
* AI features enabled for your organization. Smart Deployments uses AI to generate your configuration, so the guided setup is unavailable without it. See the xref:toolkit:enable-ai-powered-features.adoc[Enable AI-Powered Features] page for steps. Without AI features, follow the xref:set-up-deploy-validation-manually.adoc[Set up Deploy Validation Manually] guide.
* For continuous validation, a monitoring tool that can send outbound webhooks. Datadog, Prometheus, and Alertmanager are supported directly, and you can connect any other tool as a custom provider.

== Start the guided setup

You can start Smart Deployments from any of the following places in the web app:

* Your project home page. Select btn:[Smart Deployments].
* Your project deploys page, when the project has no deploys configured yet.
* Your project settings. Select *Deploys* in the sidebar, then select btn:[Smart Deployments] in the Smart Deployments card.

To reach the project settings entry point, follow these steps:

. Select *Deploys* in the sidebar.

== 1. Choose your protection level

The first step of the guided setup asks how much protection you want, and which monitoring tool sends the signals.

=== a. Select continuous validation or deploy tracking

Select *Continuous validation*, marked *Suggested*, to validate every release against your monitoring tool. Select *Deploy tracking* to record deploy markers only.

If you select deploy tracking, the guided setup skips monitoring provider selection and the Connect monitoring step. You get deploy markers, and you can return later to add validation.

=== b. Configure automatic rollback

Leave *Auto rollback on failure* enabled unless you want failure detection without an automatic revert. When the toggle is enabled, CircleCI attempts a rollback to the last healthy version if validation fails during the evaluation window.

You can also change this setting later in your configuration file. See the xref:deploy-validation-reference.adoc#optional-validation-fields[Optional Validation Fields] section.

=== c. Select a monitoring provider

Choose the provider that sends your validation webhooks:

* Datadog
* Prometheus
* Custom

You must select a provider before you continue. Provider-specific webhook instructions appear in step three, after you merge the configuration pull request. You can also finish the webhook setup later from your organization deploy settings.

=== d. Review what is added to your configuration

Expand *What we'll add to your config* to see the changes CircleCI generates:

* Deploy markers in `.circleci/config.yml`.
* A `validation` block on your release job in `.circleci/config.yml`.
* A rollback pipeline in `.circleci/rollback.yml`.
* A deploy pipeline in `.circleci/deploy.yml`.

The guided setup generates a starting configuration. You can extend it once you have reviewed the pull request. For every field you can set, see the xref:deploy-validation-reference.adoc[Deploy Validation Configuration Reference] page.

Select btn:[Generate configuration] to continue.

== 2. Generate configuration and merge the pull request

In this step CircleCI writes the generated configuration to a branch in your repository, and you review and merge it.

=== a. Select the config branch

Choose the branch that contains your `.circleci/config.yml` file. CircleCI commits the generated configuration to a branch called `circleci/deploy-setup` and targets the branch you select.

The *Ready to generate* panel confirms which configurations the pull request includes.

=== b. Generate the configuration

Select btn:[Generate configuration]. CircleCI generates each configuration in turn and shows its progress. Generation takes a few moments.

CircleCI generates the following:

* Deploy markers and a `validation` block in `.circleci/config.yml`.
* A rollback pipeline in `.circleci/rollback.yml`, when you selected that option.
* A deploy pipeline in `.circleci/deploy.yml`, when you selected that option.

=== c. Review and merge the pull request

. Select btn:[Create pull request on GitHub]. This opens GitHub with a pull request titled *Configure deploy settings*, from `circleci/deploy-setup` to the branch you selected. The pull request description contains a pre-filled verification checklist.
. Review the generated validation and deploy configuration. To check the generated commit without opening a pull request, select *View commit*.
. Address any schema validation warnings shown in the guided setup before you merge.
. Merge the pull request.
. Return to the guided setup and select btn:[I've merged the pull request].

Once you confirm the merge, CircleCI creates the rollback and deploy pipeline definitions in your project settings.

TIP: Review the generated pipelines against your deployment process before you rely on them. The generated rollback and deploy configuration is a starting point, and you will usually need to add your own authentication and deployment logic. See the xref:set-up-rollbacks.adoc#example-rollback-pipeline-configuration[Example Rollback Pipeline Configuration] and xref:set-up-deploys.adoc#example-deploy-pipeline-configuration[Example Deploy Pipeline Configuration] sections.

[#connect-monitoring-webhooks]
== 3. Connect monitoring webhooks

This step is required for continuous validation. Without it, CircleCI has no signals to evaluate and every release finishes as inconclusive.

=== a. Copy the webhook ingest URL

All validation webhooks POST to the following URL:

[source,text]
----
https://circleci.com/api/v3/deploy/hooks/<org-id>/validate
----

Replace `<org-id>` with your organization ID. The URL is the same for every webhook secret in your organization. You can copy the full URL, with your organization ID already filled in, from the guided setup or from your organization deploy settings.

include::guides:ROOT:partial$notes/find-organization-id.adoc[]

=== b. Create a webhook secret

CircleCI authenticates validation webhooks with a bearer token. Create the token in the guided setup or in your organization deploy settings.

[tabs]
====
In the guided setup::
+
--
. On the *Connect monitoring* step, select btn:[Generate webhook secret].
. Copy the secret immediately. You cannot view it again after you leave the screen.

CircleCI names the generated secret after your organization and provider, for example `my-org-datadog-webhook`.
--
In organization deploy settings::
+
--
include::guides:ROOT:partial$app-navigation/steps-to-org-settings.adoc[]
. Select *Deploys*.
. Find the Webhook secrets card.
. Select btn:[Create webhook secret].
. Enter a descriptive name, for example `Production Datadog`.
. Optionally set an expiration date.
. Copy the plaintext token before you close the modal.
--
====

CAUTION: The plaintext token is shown once. Store it in your monitoring tool or your secrets manager straight away. If you lose it, revoke the secret and create a new one.

=== c. Authenticate webhook requests

Configure your monitoring tool to send the following custom header on every validation webhook:

[source,json]
----
{
  "Authorization": "Bearer <secret>"
}
----

Replace `<secret>` with the token you copied. Do not include the angle brackets.

=== d. Configure your monitoring provider

Follow the instructions for the provider you selected in step one. Each provider needs the ingest URL, the bearer auth header, and a set of tags that let CircleCI match the alert to the right release.

include::guides:ROOT:partial$deploy/configure-validation-providers.adoc[leveloffset=+2]

=== e. Finish the setup

Select btn:[Done] to finish the guided setup.

Your next deploy through the release job starts an evaluation window and waits for signals from your monitoring tool. To check that your webhook works, trigger a test alert in your monitoring tool and look for the event in the Release Validation panel on your deployment details page.

If you closed the guided setup before you connected your monitoring tool, you can finish the webhook setup at any time from your organization deploy settings.

[#how-deploy-validation-works]
== How deploy validation works

When a deploy runs through a release job with validation enabled, the following happens:

. The deploy completes and validation starts.
. CircleCI opens an evaluation window with a deadline.
. Each webhook validation plan enters a *Listening* state.
. CircleCI evaluates incoming webhook events against the `fail_when` expression for each plan.
. Failures increment a counter until the plan reaches its `max_failures` threshold.

=== Validation outcomes

[.table-scroll]
--
[cols="1,2", options="header"]
|===
|Outcome
|What happens

|Validation passes
|The release completes successfully.

|Validation fails
|The release is marked failed. Automatic rollback may trigger.

|Automatic rollback succeeds
|The rollback pipeline runs and returns the component to the prior healthy version.

|Automatic rollback fails
|The failed rollback does not trigger another automatic rollback, even when the rollback pipeline includes validation of its own.

|Automatic rollback skipped
|No rollback runs. This happens when there is no prior successful release, or when no rollback pipeline is configured.

|Manual promote
|Validation ends early and the release is marked successful.

|Manual cancel
|Validation stops. A rollback may trigger if a prior version exists.

|Inconclusive
|No decisive result arrived within the evaluation window.
|===
--

To end validation early, use the promote or cancel actions on the deployment details page. Promoting marks the release successful, so use it when you have confirmed the release is healthy by other means.

=== View validation results

Open a deployment from the deploys timeline to see its Release Validation panel. The panel shows the following:

* The overall validation status, evaluation deadline, start time, and the number of validations and failures.
* A progress bar for the evaluation window, with the start time and deadline.
* Each validation plan, with its status, failure count against the maximum, and its `fails when` expression.
* The webhook events received for each plan, and whether each event matched the fail criteria.

If validation fails, a banner at the top of the page names the plan that failed and the expression that matched.

== Manage Smart Deployments settings

=== Change your protection level

Your protection level is a configuration setting, not a one-time choice. To move from deploy tracking to continuous validation, or to turn validation off, edit the `validation` block on your release job. See the xref:deploy-validation-reference.adoc[Deploy Validation Configuration Reference] page.

You can also run the guided setup again from project settings.

=== Manage webhook secrets

To view, create, or revoke webhook secrets, follow these steps:

include::guides:ROOT:partial$app-navigation/steps-to-org-settings.adoc[]
. Select *Deploys*.
. Find the Webhook secrets card. The table lists each secret with its name, creation date, last used date, and expiry date.
. Select btn:[Revoke] to revoke a secret.

Revoking a secret takes effect immediately. Any monitoring tool still sending that token stops being able to deliver validation webhooks, so update your monitoring tool before you revoke.

=== Set the inconclusive release timeout

A release that receives no decisive signal stays in an inconclusive state until it times out. Configure how long CircleCI waits before it cancels the release automatically, as follows:

include::guides:ROOT:partial$app-navigation/steps-to-org-settings.adoc[]
. Select *Deploys*.
. Find the Inconclusive Release Timeout card.
. Choose a value from the dropdown menu. When you set no custom value, CircleCI uses the system default of four hours.
