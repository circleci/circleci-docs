[#namespaces-and-resource-classes]
== Namespaces and resource classes

Self-hosted runners require both a namespace and a resource class.

A **namespace** is a unique identifier claimed by a CircleCI organization. Each CircleCI organization can claim one unique and immutable namespace. Typically, the namespace chosen is the lowercase representation of your organization's name on your VCS (this is suggested).

A **resource class** is a label to match your CircleCI job with a type of runner that is identified to process that job. The first part of the resource class is your organization's namespace. For example, a CircleCI resource class could be `circleci/documentation`. Resource classes are created when you go through the process of installing self-hosted runners.

Resource classes help you identify a pool of self-hosted runners, which allows you to set up your configuration to send jobs to specific places. For example, if you have multiple machines running macOS, and multiple machines running Linux, you could create resource classes for each of these, `orgname/macOS` and `orgname/linux`, respectively. At the job level in your `.circleci/config.yml`, you can associate which self-hosted runner resources to send a job to based on the resource class.

Optionally, you can give your resource class a description.

Every resource class has one or more **resource class tokens**. CircleCI uses the token to authenticate that the resource class is valid. A resource class token can only claim tasks.

== Tasks

A task is the smallest unit of work on CircleCI. A job with xref:guides:optimize:parallelism-faster-jobs.adoc[Parallelism] of one is one task. A job with parallelism of _n_, where _n_ is greater than one, creates _n_ tasks.

NOTE: If you are already using xref:orbs:use:orb-intro.adoc[Orbs], you have an existing namespace. Your self-hosted runner namespace will be the same one you are using for orbs. If you need to change your namespace, https://support.circleci.com/hc/en-us[Contact Support].

[#task-agent]
== Task-agent

The task-agent handles running a task retrieved and configured by the container runner or machine runner. Task-agents run with the same privileges as `circleci`.

[#container-agent]
== Container-agent

The container-agent gets installed with container runner. Container-agent polls CircleCI for jobs, spins up ephemeral pods with an injected task-agent, and executes each job within each pod. The pods are torn down after the jobs have completed.

[#machine-runner-3]
== Machine runner 3

The machine runner 3 replaces launch-agent on cloud and server v4.4+, bringing improvements to network resiliency, installation, and the upgrade process. As with launch-agent, any user who is able to execute a job will be able to gain the same privileges as the task-agent. When machine runner is installed using the provided packages, it runs as the `circleci` user. You choose the user that executes jobs when you install the runner, so make sure that user only has permissions you are comfortable letting jobs use.

CAUTION: Allowing jobs to access a Docker daemon is equivalent to providing root access to the machine.

A container runner also lets users run arbitrary code in your infrastructure. Follow security best practices to limit what that code can reach.

[#self-hosted-runner-concurrency]
== Self-hosted runner concurrency

CircleCI's self-hosted runners are limited by the total number of self-hosted runner jobs (tasks) across your organization.

[#public-repositories]
== Public repositories

CircleCI's self-hosted runners are not available for use with public projects that have the **Build forked pull requests** setting enabled. This feature is not available for security reasons. A malicious actor may alter your machine or execute code on it by forking your repository, committing code, and opening a pull request. Untrusted jobs running on your self-hosted runner pose significant security risks for your machine and network environment, especially if your machine persists its environment between jobs. Some of the risks include:

* Malicious programs running on the machine.
* Escaping the machine's self-hosted runner sandbox.
* Exposing access to the machine's network environment.
* Persisting unwanted or dangerous data on the machine.

Resource classes cannot be used by jobs that are not associated with the organization that owns them. Only forks of your open source project that are part of your organization can use the organization's self-hosted runners.

NOTE: Organizations are, by default, limited to claiming only one namespace. This policy is designed to limit name-squatting and namespace noise. If you need to change your namespace, https://support.circleci.com/hc/en-us[contact support].

== Manage resource classes and tokens

Organization admins in your VCS provider can create and delete resource classes. Any organization user in your VCS provider that the resource class is associated with can view the resource class list with the CLI.

Use the xref:guides:toolkit:circleci-cli.adoc[CircleCI CLI] to manage resource classes and their tokens.

=== Delete a resource class

Deleting a resource class is permanent. Without `--force`, the command prompts for confirmation and fails while the resource class has tokens. With `--force`, the command skips the prompt and deletes the tokens too, so runners that use them cannot claim jobs.

[source,console]
----
$ circleci runner resource-class delete <resource-class> --force
----

[#create-a-token]
=== Create an additional token

The CLI shows the token value once, when you create the token. You cannot retrieve it afterwards.

[source,console]
----
$ circleci runner token create <resource-class> --nickname <nickname>
----

=== Delete a token

Deleting a token is permanent. It does not delete the resource class. Runners that use the token cannot claim jobs, but running jobs continue.

List the tokens and their IDs:

[source,console]
----
$ circleci runner token list <resource-class>
----

Delete the token. Add `--force` to skip the confirmation prompt:

[source,console]
----
$ circleci runner token delete <token-id>
----
